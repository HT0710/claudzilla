# Blueprint reference

Read the section a case needs. The flow in `SKILL.md` still applies.

## Non-code projects

- Ask where the user keeps notes, and put the spec there or in the job folder.
- Size by effort: one sitting with a clear done is small; several sittings or an unclear done is a project.
- The Verify section is a checklist the user can tick, not a command.
- The builder check addresses "the person who will do this" instead of a software engineer, with the domain filled in to match.

## How it gets made

- A user who talks in outcomes hands you the tools and the medium. State each such call in one line they can correct.
- A user who asks about tools gets the options as a Decision, with a pick.

## Ground to cover

Cover these over the conversation, without reading them out as a list of questions:

- the goals, and what is out of scope;
- prior art the user liked or disliked;
- the current state, and what already works.

## Spikes

- Offer a spike when a quick throwaway build answers the question faster than talking.
- A spike gets no tests and no plan.
- Keeping any of it is a new request, and it goes through the gate like any other.

## Requests that grow

When a request grows mid-design, step it up a size and say so in one line. A small change that turns into a project gets the full spec and the builder check.
